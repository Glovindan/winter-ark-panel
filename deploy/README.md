# Деплой и CI/CD

## Как это устроено

- **CI** (`.github/workflows/ci.yml`): на каждый push и pull request: типы, тесты, сборка фронтенда, тест скрипта раскатки.
- **CD**: после зелёного CI на `main` сборка уходит на сервер одной SSH-командой. Деплой включается переменной репозитория `DEPLOY_ENABLED=true`; пока её нет, workflow только проверяет код.
- **Релизы на сервере**: `/opt/ark/releases/<время>` и симлинк `/opt/ark/current`. Новый релиз ставится рядом со старым, переключение атомарное, после перезапуска проверяется `/health`, при сбое симлинк возвращается назад автоматически. Хранятся 3 последних релиза.
- **Перед каждым деплоем** снимается копия базы: `/var/lib/ark/backups/pre-deploy-<время>.db` (хранятся последние 5).
- **Ключ CI** на сервере может выполнить только `ark-deploy` (принять архив и раскатать). Оболочки и других команд по нему нет. Сами скрипты `update.sh` и `ark-deploy` принадлежат root, CI их изменить не может.

## Однократная настройка

### 1. Ключ для CI (на твоём компьютере)

```bash
ssh-keygen -t ed25519 -N "" -C "github-ci" -f "%USERPROFILE%\.ssh\ark_ci"
```

Создадутся `ark_ci` (приватный, никому не показывать) и `ark_ci.pub` (публичный).

### 2. Перевод сервера на релизную схему

Скрипт переносит текущую установку в `releases/0000-legacy`, переключает службу и Caddy на `current`, сервис недоступен несколько секунд. Если после миграции сервис не поднимется, всё возвращается как было.

```bash
scp deploy/server/update.sh deploy/server/ark-deploy.sh deploy/server/install-ci.sh root@2.27.10.152:/tmp/
```

```bash
ssh root@2.27.10.152 "cd /tmp && bash install-ci.sh \"$(type %USERPROFILE%\.ssh\ark_ci.pub)\""
```

(Если вторая команда капризничает с кавычками в `cmd`, зайди на сервер по ssh, вставь публичный ключ в `nano /tmp/ci.pub` и выполни `cd /tmp && bash install-ci.sh "$(cat /tmp/ci.pub)"`.)

### 3. Настройки GitHub

В репозитории: **Settings → Secrets and variables → Actions**.

Secrets:

| Имя | Значение |
|---|---|
| `DEPLOY_SSH_KEY` | содержимое файла `ark_ci` (приватный ключ целиком) |
| `DEPLOY_HOST` | `2.27.10.152` |
| `DEPLOY_USER` | `root` |
| `DEPLOY_KNOWN_HOSTS` | вывод `ssh-keyscan -t ed25519 2.27.10.152` |

Variables: `DEPLOY_ENABLED` = `true`.

Рекомендуется: **Settings → Environments → production → Required reviewers** (добавь себя). Тогда каждый деплой будет ждать твоего подтверждения.

## Ручной деплой

Если CI недоступен, с компьютера (после шага 2):

```powershell
.\deploy\deploy.ps1 -Server 2.27.10.152
```

## Откат вручную

Автоматический откат срабатывает при неудачном запуске. Если проблема в логике, а не в запуске:

```bash
ls /opt/ark/releases                      # список релизов
ln -sfn /opt/ark/releases/<предыдущий> /opt/ark/current && systemctl restart ark
```

База: миграции только добавляют таблицы и колонки, поэтому старый код работает на новой схеме. Если нужно вернуть и данные: остановить `ark`, скопировать нужный `pre-deploy-*.db` поверх `/var/lib/ark/ark.db` (с владельцем `ark`), запустить `ark`.

## Что нельзя менять без повторного шага 2

`update.sh`, `ark-deploy.sh` и `install-ci.sh` ставятся на сервер вручную. Изменения в них не уезжают с CI, это намеренно: CI не должен уметь переписывать собственные привилегированные скрипты.
